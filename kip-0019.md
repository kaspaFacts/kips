# Motivation

Proof of inclusion provides a mechanism for applications to verify that a specific transaction was included in the Kaspa
DAG without requiring access to the full blockchain history. This enables lightweight verification of transaction
status, audit trails, and proof of payment systems among many possible use-cases.

While KIP-15 provides sequencing commitments for comprehensive transaction indexing, this KIP focuses specifically on
efficient single-transaction inclusion proofs that users can generate and store independently.

Critically, anyone with this proof can then use data preserved by a Kaspa full node to verify inclusion, enabling
efficient verification without needing archival nodes or complete blockchain data. This approach leverages the existing
infrastructure of full nodes while providing cryptographic guarantees of transaction inclusion.

This document aims to provide a standard which applications can implement to generate, store, and verify inclusion
proofs efficiently, particularly before relevant data is pruned from the network. The protocol will define the proof
structure, calculation methodology, storage requirements, and recommended formats to ensure interoperability across
different Kaspa applications and services.

# Specifications

## Proof Structure Overview

KIP-19 defines a standardized format for cryptographic proofs that demonstrate transaction inclusion in the Kaspa DAG.
The proof system enables verification without requiring full blockchain access by leveraging preserved consensus data
and efficient cryptographic commitments.

## Core Components

### Transaction Data

Full transaction bytes serialized according to the Kaspa transaction format:

- **Version** (2 bytes, little-endian)
- **Number of inputs** (varint) + input details including previous outpoint, signature script, sequence
- **Number of outputs** (varint) + output details including value, script public key
- **Lock time** (8 bytes, little-endian)
- **Subnetwork ID** (16 bytes)
- **Gas** (8 bytes, little-endian)
- **Payload** (varint length + bytes)
- Excludes: SigOp count, Mass commitment

**Encoding flags**:

- Coinbase transactions: `TxEncodingFlags::FULL` (includes signature script)
- Non-coinbase transactions: `TxEncodingFlags::EXCLUDE_SIGNATURE_SCRIPT | TxEncodingFlags::EXCLUDE_MASS_COMMIT`

### Merkle Proof

Path from transaction ID to the block's Accepted ID Merkle Root (ATMR):

- Uses **sorted Transaction IDs** from the accepting block's mergeset
- Transaction IDs are sorted before merkle root calculation
- Always use Transaction IDs, not full transaction hashes for proofs

### Clarification: SequencingCommitment and Accepted ID Merkle Root

**Note on Terminology**: Throughout this document, the term "SequencingCommitment" refers to the existing
`accepted_id_merkle_root` field in Kaspa block headers. These terms are used interchangeably - the SequencingCommitment
chain described in this KIP is the existing accepted ID merkle root chain already implemented in the Kaspa codebase.

#### Accepted ID Merkle Root Construction

Kaspa creates each block's `accepted_id_merkle_root` by combining two values:

```rust  
kaspa_merkle::merkle_hash(  
    self.headers_store.get_header(selected_parent).unwrap().accepted_id_merkle_root,  
    kaspa_merkle::calc_merkle_root(accepted_tx_ids),  
)  
```  

1. **Selected parent's accepted ID merkle root** - Retrieved from the parent block header
2. **Current block's accepted transaction IDs merkle root** - Calculated from sorted transaction IDs in the current
   block's mergeset

#### Chain Verification Entry Point

The accepting block's selected parent `accepted_id_merkle_root` serves as the entry point for chain verification
because:

- Each block's `accepted_id_merkle_root` incorporates its selected parent's `accepted_id_merkle_root`
- This creates a verifiable chain of commitments from any block back to the pruning point
- Walking this chain proves the accepting block is in the selected chain without requiring full blockchain history

The verification process walks the `accepted_id_merkle_root` chain from the accepting block to the pruning point, using
preserved block headers stored by full nodes.

### Temporal Verification

Inclusion proofs provide three levels of temporal guarantees, allowing applications to verify not just that a
transaction was included, but also approximately when it occurred:

#### 1. Rough Time Zone (Pruning Point Window)

- **Verification Method**: Walk the SequencingCommitment chain from the including block to the pruning point
- **Temporal Precision**: Proves inclusion occurred between two consecutive pruning points
- **Window Size**: Approximately 185,000 blocks (~2 days at 10 BPS)
- **Data Required**: Only the SequencingCommitment chain and pruning point data
- **Implementation**: Uses the immutable `accepted_id_merkle_root` chain where each block incorporates its parent's
  commitment

#### 2. Exact Time (Block Timestamp)

- **Verification Method**: Preserve and verify the full block header containing the timestamp
- **Temporal Precision**: Millisecond-precision wall-clock time
- **Data Required**: Complete block header for the including block
- **Implementation**: Block headers store timestamps in milliseconds
- **Considerations**: Assumes timestamp accuracy; may be affected by clock variations

#### 3. DAA Time (Difficulty-Adjusted Time)

- **Verification Method**: Use the DAA score from the block header
- **Temporal Precision**: Network-consistent expected block time
- **Data Required**: Block header DAA score field
- **Implementation**: Headers contain DAA score representing network time
- **Advantages**: More stable than wall-clock time across network conditions and difficulty adjustments

**Implementation Recommendation**: Applications SHOULD document which temporal precision level they support and preserve
corresponding data (pruning point index for rough timing, block headers for exact timing, or both).

### Pruning Point Index Preservation

**Performance Optimization**: Implementations SHOULD preserve the pruning point index alongside the hash to enable O(1)
lookup of historical pruning points.

#### Technical Details

- **Storage Method**: The `past_pruning_points_store` uses a simple index-to-hash mapping
- **Lookup Performance**: Index-based lookup provides constant time access vs O(n) linear search by hash
- **Index Assignment**: Sequential assignment during pruning point advancement
- **Storage Format**: `index → hash` mapping where index starts at 0 (genesis) and increments monotonically

#### Benefits

1. **Verification Speed**: Dramatically improves verification performance for historical proofs
2. **Simplified Logic**: Eliminates need for complex hash-based search algorithms
3. **Predictable Access**: Enables efficient range queries and batch verification
4. **Minimal Overhead**: Index is a simple 64-bit integer per pruning point

#### Implementation Example

```rust  
// Store pruning point with index  
past_pruning_points_store.insert(index, pruning_point_hash);  
  
// O(1) lookup by index  
let historical_pp = past_pruning_points_store.get(target_index);  
```  

**Critical for**: Applications verifying inclusion proofs against historical pruning points, especially in batch
scenarios or when processing large numbers of proofs.

### Chain Verification

Proof that the accepting block is in the selected chain:

- Walk up **SequencingCommitment** chain to pruning point block
- Requires **selected parent's SequencingCommitment** for proof entry point
- SequencingCommitment calculation: `hash(SelectedParent.SequencingCommitment, AcceptedIDMerkleRoot)`

### Pruning Point Data

- **Header ID** (hash) for search optimization
- **SequencingCommitment** of the pruning point
- Full block header for complete verification

## Block Header Structure

The Kaspa block header contains 13 fields serialized in specific order:

| Field                   | Type              | Size     | Description                        |  
|-------------------------|-------------------|----------|------------------------------------|  
| version                 | u16               | 2 bytes  | Block version number               |  
| parents_by_level        | CompressedParents | Variable | Compressed parent hashes           |  
| hash_merkle_root        | Hash              | 32 bytes | Merkle root of transaction hashes  |  
| accepted_id_merkle_root | Hash              | 32 bytes | Merkle root of transaction IDs     |  
| utxo_commitment         | Hash              | 32 bytes | UTXO set commitment                |  
| timestamp               | u64               | 8 bytes  | Block timestamp in milliseconds    |  
| bits                    | u32               | 4 bytes  | Difficulty target                  |  
| nonce                   | u64               | 8 bytes  | Proof-of-work nonce                |  
| daa_score               | u64               | 8 bytes  | Difficulty adjustment score        |  
| blue_work               | BlueWorkType      | Variable | Blue work value                    |  
| blue_score              | u64               | 8 bytes  | Blue score                         |  
| pruning_point           | Hash              | 32 bytes | Pruning point hash                 |  
| hash                    | Hash              | 32 bytes | Cached block hash (not serialized) |  

## Multi-Transaction Support

### Batch Proof Structure

Single proof can contain multiple transactions spanning multiple blocks:

- **Shared chain components**: Single SequencingCommitment proof from oldest transaction's block to pruning point
- **Individual transaction data**: Full transaction bytes for each transaction
- **Individual merkle proofs**: Separate proofs for each transaction to its respective ATMR

### Size Efficiency

- First transaction: Full proof size (~10KB)
- Each additional transaction: Only individual merkle proof (~1KB each)
- Shared chain components amortized across all transactions

## Branch Trimming

Proofs support dynamic removal of individual transaction proofs:

- Remove transaction data and merkle proof for specific transactions
- Preserve shared chain components for remaining transactions
- Enables efficient proof size reduction when individual transactions are no longer needed

## Verification Process

### Required Data

- **Inclusion proof**: Complete proof structure as defined above
- **Posterity headers**: Preserved by full nodes for chain verification
- **Pruning point data**: Header and SequencingCommitment for final verification

### Verification Steps

1. **Transaction verification**: Recreate transaction ID from serialized data
2. **Merkle proof verification**: Verify transaction ID inclusion in ATMR
3. **Chain verification**: Walk SequencingCommitment chain to pruning point
4. **Consensus validation**: Verify against preserved posterity headers

### Optimization

- Provide pruning point block hash to optimize header search
- Use full node's preserved posterity headers for efficient verification

## Hash Function Specifications

### Blake2b Parameters

- **Algorithm**: Blake2b
- **Digest size**: 32 bytes
- **Key**: Domain separation keys for different purposes
- **Endian**: Little-endian for multi-byte numeric fields
- **Hash order**: Natural byte order for hash fields

### Domain Separation

Different Blake2b keys prevent confusion between proof types:

- Message signing: `PersonalMessageSigningHash`
- Transaction signing: `TransactionSigningHash`
- Inclusion proofs: `TransactionID` and `MerkleBranchHash`

## Data Formats

### Serialization Order

All multi-byte numeric fields use little-endian encoding except hashes which use natural byte order.

### Proof Format

```rust  
Proof {  
  version: u16,  
  proof_type: u8,  
  transactions: Vec<TransactionProof>,  
  chain_proof: ChainProof,  
  pruning_point: PruningPointData  
}
```

### TransactionProof Format

```rust    
TransactionProof {      
  transaction_data: Vec<u8>,      
  merkle_proof: Vec<Hash>,      
  block_header: Header,      
  selected_parent_seqcommit: Hash      
}
```

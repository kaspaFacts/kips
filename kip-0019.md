# Motivation  

Proof of inclusion provides a mechanism for applications to verify that a specific transaction was included in the Kaspa DAG without requiring access to the full blockchain history. This enables lightweight verification of transaction status, audit trails, and proof of payment systems among many possible use-cases.

While KIP-15 provides sequencing commitments for comprehensive transaction indexing, this KIP focuses specifically on efficient single-transaction inclusion proofs that users can generate and store independently.

Critically, anyone with this proof can then use data preserved by a Kaspa full node to verify inclusion, enabling efficient verification without needing archival nodes or complete blockchain data. This approach leverages the existing infrastructure of full nodes while providing cryptographic guarantees of transaction inclusion.

This document provides a standard for applications to generate, store, and verify inclusion proofs with cryptographic security guarantees, particularly before relevant data is pruned from the network. The protocol defines the proof structure, verification requirements, and interoperability standards to ensure compatibility across different Kaspa applications and services.

# Specifications  
  
## Proof Structure Overview  

KIP-19 defines a standardized format for cryptographic proofs that demonstrate transaction inclusion in the Kaspa DAG. The proof system enables verification without requiring full blockchain access by leveraging preserved consensus data and efficient cryptographic commitments.

### Standardized format for cryptographic proofs  
  
## Core Components  

### Transaction Data  

Full transaction bytes serialized according to the Kaspa transaction format, including all standard fields (version, inputs, outputs, lock time, subnetwork ID, gas, payload).

### Merkle Proof  

Path from transaction ID to the block's Accepted ID Merkle Root (ATMR):

- Uses **sorted Transaction IDs** from the accepting block's mergeset
- Transaction IDs are sorted before merkle root calculation
- Always use Transaction IDs, not full transaction hashes for proofs

### Clarification: SequencingCommitment and Accepted ID Merkle Root  

**Note on Terminology**: Throughout this document, the term "SequencingCommitment" refers to the existing
`accepted_id_merkle_root` field in Kaspa block headers. These terms are used interchangeably - the SequencingCommitment
chain described in this KIP is the existing accepted ID merkle root chain already implemented in the Kaspa codebase.

## Data Formats  

### Serialization Order  

All multi-byte numeric fields use little-endian encoding except hashes which use natural byte order.

### Proof Structure  

- **version**: Protocol version number  
- **proof_type**: Single or batch proof indicator  
- **transactions**: Array of transaction proofs  
- **chain_proof**: SequencingCommitment chain data  
- **pruning_point**: Pruning point reference data  
  
# Pruning Point System  

The `PastPruningPointsStore` is an append-only database store that maintains a permanent, indexed record of all historical pruning points in Kaspa. Each entry represents a block selected as a pruning point and is preserved forever, even as other block data at those heights gets pruned.  
  
## Accepted ID Merkle Root Construction  

Kaspa creates each block's `accepted_id_merkle_root` by combining:  
1. **Selected parent's accepted ID merkle root** - Retrieved from the parent block header  
2. **Current block's accepted transaction IDs merkle root** - Calculated from sorted transaction IDs in the current block's mergeset

## Chain Verification Entry Point  

The accepting block's selected parent `accepted_id_merkle_root` serves as the entry point for chain verification because:

- Each block's `accepted_id_merkle_root` incorporates its selected parent's `accepted_id_merkle_root`
- This creates a verifiable chain of commitments from any block back to the pruning point
- Walking this chain proves the accepting block is in the selected chain without requiring full blockchain history

The verification process walks the `accepted_id_merkle_root` chain from the accepting block to the pruning point, using preserved block headers stored by full nodes.

## Index-Based Organization  

The store uses a simple index-to-hash mapping structure for O(1) lookup performance:  
- **Index 0**: Always contains the genesis block hash  
- **Sequential indexing**: Each new pruning point receives the next available index (1, 2, 3, ...)  
- **Monotonic growth**: Indices never decrease or are reused  
  
This indexing dramatically improves verification performance for historical proofs and enables efficient range queries and batch verification.  

## Block Entry Criteria  

A block enters the PastPruningPointsStore when it satisfies these conditions:  
  
1. **Pruning Sample Eligibility**: `finality_score(block) > finality_score(selected_parent)` where `finality_score = blue_score / finality_depth`  
2. **Sufficient Depth**: At least `pruning_depth` blocks behind the current tip/virtual state  
3. **Chain Selection**: On the selected chain from the current tip  
4. **Finalization**: Achieved sufficient burial depth to mitigate reorg risks  

## Storage Mechanisms  

Blocks are added through three primary mechanisms:  
- **Normal Pruning Point Advancement**: When the network advances and identifies new pruning points  
- **Genesis Initialization**: At node startup, genesis is stored at index 0  
- **IBD/Catchup Sync**: When importing pruning points during initial block download  

## Preservation Guarantees  

Once stored, pruning points are preserved permanently:  
- Headers are never pruned from these indices  
- The store is append-only with no deletion mechanism  
- This enables long-term verification of historical inclusion proofs  

## Pruning Point Data  

Each stored pruning point contains:  
- **Header ID** (hash) for search optimization  
- **SequencingCommitment** of the pruning point  
- Full block header for complete verification  
  
The PastPruningPointsStore serves as the foundation for KIP-19 verification, allowing proofs to anchor to any historical pruning point while maintaining verifiability without requiring full archival nodes.
  
# Chain Verification  

Verify the accepting block is in the selected chain by walking the SequencingCommitment chain from the selected parent to the pruning point. Each SequencingCommitment is calculated as `hash(SelectedParent.SequencingCommitment, AcceptedIDMerkleRoot)`.  
  
## Verification Steps  

1. Start from the accepting block's selected parent SequencingCommitment  
2. Walk forward through the chain of commitments  
3. Each step verifies: `current_seqcommit = hash(prev_seqcommit, block_accepted_id_merkle_root)`  
4. Continue until reaching the pruning point's SequencingCommitment  
5. Verify the pruning point exists in PastPruningPointsStore
  
# Temporal Verification  

Inclusion proofs provide three levels of temporal guarantees for verifying when a transaction occurred.
  
Applications SHOULD document whether they provide temporal estimates tighter than the 12-hour pruning point window.
 
## Rough Time Zone  

Walk the SequencingCommitment chain to prove inclusion between pruning points (~12-hour window). Requires only pruning point index.

## Estimated Wall Clock Time  

Estimate timestamp based on ATMR count between transaction block and pruning point, using average block rate and DAG width assumptions. Requires no additional preserved data.

## Estimated DAA Time  

Estimate DAA score based on ATMR count between transaction block and pruning point, using the same block rate and width assumptions. Requires no additional preserved data.

## Security Note  

Full block headers cannot provide guaranteed timestamp or DAA accuracy without preserving all intermediate headers for verification. Both wall clock and DAA time estimation use the same secure ATMR-based approach, leveraging the cryptographic commitment chain for temporal accuracy.

# Cryptographic Commitments in Block Headers  

KIP-19 leverages Kaspa's block header commitments for secure inclusion proofs. While headers contain 13 fields, only the `accepted_id_merkle_root` (SequencingCommitment) is used in KIP-19 proofs.

## Security Model  

Any header field can contain arbitrary data with valid PoW. Without preserving the complete header chain to a permanent pruning point, such data cannot be verified and could be forged. KIP-19 achieves security by preserving the ATMR (accepted_id_merkle_root) chain from the transaction block to a permanent pruning point, creating a verifiable cryptographic commitment that proves transaction data authenticity.

## Key Field  

The `accepted_id_merkle_root` provides the essential cryptographic commitment linking transactions to the chain, enabling verification without requiring full archival data.

# Verification Process  
  
## Required Data  

- **Inclusion proof**: Complete proof structure as defined above
- **Posterity headers**: Preserved by full nodes for chain verification
- **Pruning point data**: Header and SequencingCommitment for final verification

## Verification Steps  

1. **Transaction verification**: Recreate transaction ID from serialized data
2. **Merkle proof verification**: Verify transaction ID inclusion in ATMR
3. **Chain verification**: Walk SequencingCommitment chain to pruning point
4. **Consensus validation**: Verify against preserved posterity headers

## Optimization  

- Provide pruning point block hash to optimize header search
- Use full node's preserved posterity headers for efficient verification
  
# Multi-Transaction Support  
  
## Batch Proof Structure  

Single proof can contain multiple transactions spanning multiple blocks:  
  
- **Shared chain components**: Single SequencingCommitment proof from oldest transaction's block to pruning point  
- **Individual transaction data**: Full transaction bytes for each transaction  
- **Individual merkle proofs**: Separate proofs for each transaction to its respective ATMR  

## Size Efficiency  

Batch proofs provide significant efficiency by amortizing the chain verification cost across multiple transactions. The first transaction requires the full chain proof, while additional transactions only need their individual merkle proofs and transaction data.  

## Branch Trimming  

Proofs support dynamic removal of individual transaction proofs:  
  
- Remove transaction data and merkle proof for specific transactions  
- Preserve shared chain components for remaining transactions  
- Enables efficient proof size reduction when individual transactions are no longer needed

Little-endian for numeric fields, natural byte order for hashes

# Security Considerations  
 
## Proof forgery resistance  

Merkle proofs provide logarithmic security - forging requires finding hash collisions in the Blake2b hash function.

## Domain separation security  

Blake2b domain separators (`TransactionID`, `MerkleBranchHash`) prevent cross-protocol attacks between signing and proof systems.

## Chain verification attacks  

The SequencingCommitment chain is cryptographically committed and cannot be forged without solving PoW for each block in the chain.

## Privacy implications  

Inclusion proofs reveal complete transaction data including amounts, parties, and script details, since full transaction bytes are required to recreate the transaction ID for merkle proof verification.
  
# Resource Analysis  
  
## Proof Size Estimates  

Chain proof dominates total proof size, with merkle proof adding minimal overhead. Exact sizes vary based on network conditions and implementation choices.

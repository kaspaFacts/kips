# Motivation  

Proof of inclusion provides a mechanism for applications to verify that a specific transaction was included in the
Kaspa DAG without requiring access to the full blockchain history. This enables lightweight verification of transaction
status, audit trails, and proof of payment systems among many possible use-cases.

While KIP-15 provides sequencing commitments for comprehensive transaction indexing, this KIP focuses specifically on
efficient single-transaction inclusion proofs that users can generate and store independently.

Critically, anyone with this proof can then use data preserved by a Kaspa full node to verify inclusion, enabling
efficient verification without needing archival nodes or complete blockchain data. This approach leverages the existing
infrastructure of full nodes while providing cryptographic guarantees of transaction inclusion.

This document provides a standard for applications to generate, store, and verify inclusion proofs with cryptographic
security guarantees, particularly before relevant data is pruned from the network. The protocol defines the proof
structure, verification requirements, and interoperability standards to ensure compatibility across different Kaspa
applications and services. 

# Notations  
  
This section defines the terminology and notations used throughout KIP-19 for clarity and consistency.  
  
## Block and Transaction Notations  
  
- **TX_BLOCK**: The block that accepts the transaction being proved  
- **P**: The next permanent pruning point relative to TX_BLOCK  
  
## Key Terminology  
  
### SequencingCommitment and AcceptedIDMerkleRoot
  
**SequencingCommitment**: Refers to the existing `accepted_id_merkle_root` field in Kaspa block headers. This is the
cryptographic commitment that chains transactions together in the selected chain by recursively committing to the full
ordered transaction history.  
  
**AcceptedIDMerkleRoot**: The Merkle root calculated from consensus-ordered Transaction IDs in the mergeset of the
accepting block (including the selected parent). This is then hashed with the selected parent's SequencingCommitment to
generate the current block's SequencingCommitment.
  
**Relationship**: `SequencingCommitment = hash(SelectedParent.SequencingCommitment, AcceptedIDMerkleRoot)`

## Proof Structure Notations
  
- **ProofOfInclusion**: The complete proof structure containing all necessary data for verification  
- **tx_inclusion_proof**: A standard Merkle tree inclusion proof consisting of the target transaction ID and the sibling
hashes needed to verify that this transaction ID was used in calculating the accepting block's AcceptedIDMerkleRoot. The
proof demonstrates that the transaction is part of the consensus-ordered transaction set that commits to the block's
position in the chain.  
- **chain_proof_to_pruning_point**: A specialized Merkle proof that demonstrates the accepting block's position in the
selected chain. Rather than proving inclusion in a tree, it proves the sequential hash relationship: each block's
SequencingCommitment = hash(parent.SequencingCommitment, block.AcceptedIDMerkleRoot), forming an unbroken cryptographic
chain to the pruning point.  
- **future_pruning_point_index**: Index used for efficient pruning point lookup

### Proof Node Types  
- **TransactionProofNode**: Includes hash and direction (is_right) for tree inclusion verification  
- **ChainProofNode**: Optimized to include only hash, as direction is calculated sequentially

# Specifications  
  
## Proof Structure Overview  

KIP-19 defines a standardized format for cryptographic proofs that demonstrate transaction inclusion in the Kaspa DAG.
The proof system enables verification without requiring full blockchain access by leveraging preserved consensus data
and efficient cryptographic commitments.

## Simple Proof Example  
  
For a transaction included in block B with pruning point P:  
1. Prove transaction ID in B.AcceptedIDMerkleRoot (tx_inclusion_proof)  
2. Prove B connects to P through commitment chain (chain_proof_to_pruning_point)

### Standardized format for cryptographic proofs  

The standardized format includes:  
- Transaction data and Merkle proof for inclusion verification  
- Chain proof connecting to a permanent pruning point  
- Metadata for efficient lookup and validation  
- Checksum fields for integrity verification
 
## Core Components  

### Transaction Data  

Full transaction bytes serialized according to the Kaspa transaction format, including all standard fields (version,
inputs, outputs, lock time, subnetwork ID, gas, payload).

### Merkle Proof  

Path from transaction ID to the block's AcceptedIDMerkleRoot:

- Uses **consensus-ordered Transaction IDs** from the accepting block's mergeset
- Transaction IDs are consensus-ordered before merkle root calculation
- Always use Transaction IDs, not full transaction hashes for proofs

## Data Formats  

### Serialization Order  

All multi-byte numeric fields use little-endian encoding except hashes which use natural byte order.

# Chain Verification  

Verify the accepting block is in the selected chain by walking the SequencingCommitment chain from the selected parent
to the pruning point. Each SequencingCommitment is calculated as
`hash(SelectedParent.SequencingCommitment, AcceptedIDMerkleRoot)`.  
  
## Verification Steps  

1. Start from the accepting block's selected parent SequencingCommitment    
2. Walk forward through the chain of commitments    
3. Each step verifies: `current.SequencingCommitment = hash(parent.SequencingCommitment, current.AcceptedIDMerkleRoot)`    
4. Continue until reaching the pruning point's SequencingCommitment    
5. Verify the pruning point exists in PastPruningPointsStore
  
# Temporal Verification    
  
Inclusion proofs provide three methods for estimating when a transaction occurred, all available once the proof is
verified against a pruning point.  
   
## Rough Time Zone    
  
Inclusion proof verifies inclusion between pruning points (~pruning point interval window). Requires only pruning point
index.  
  
## Estimated Wall Clock Time    
  
Estimate timestamp based on AcceptedIDMerkleRoot count between transaction block and pruning point, using average block
rate and DAG width assumptions. These estimates assume relatively stable network conditions and may be less accurate
during periods of high network congestion or unusual block patterns. Requires no additional preserved data.

## Estimated DAA Time    
  
Estimate DAA score based on AcceptedIDMerkleRoot count between transaction block and pruning point, using the same block
rate and width assumptions. These estimates assume relatively stable network conditions and may be less accurate during
periods of high network congestion or unusual block patterns. Requires no additional preserved data.  

## Security Note    
  
Full block headers cannot provide guaranteed timestamp or DAA accuracy without preserving all intermediate headers for
verification. Both wall clock and DAA time estimation use the same secure AcceptedIDMerkleRoot-based approach,
leveraging the cryptographic commitment chain for temporal accuracy.

**Timestamp Accuracy Limitation**: The pruning point timestamp may deviate from actual time by up to the network's
timestamp deviation tolerance. This deviation can result from factors such as clock synchronization differences between
nodes or the time elapsed between template creation and successful mining, and is permitted as long as the block remains
valid according to consensus rules. Consequently, wall clock time estimates derived from pruning point timestamps
inherit this potential inaccuracy, while DAA-based estimates remain unaffected by timestamp variations.

# Proof Generation Timing  
  
Applications can begin generating proofs immediately after transaction acceptance, using incremental verification to
ensure the chain remains stable. Proof generation involves obtaining AcceptedIDMerkleRoot values for blocks between the
accepting block and the next pruning point, with data retrieval operations subject to network constraints.  
  
Applications MUST ensure proofs are verified against a pruning point that has achieved finality before the relevant data
is pruned from the network.
  
## Incremental Proof Generation with Chain Verification        
  
Applications can generate proofs incrementally by:      
      
1. **Early Start**: Begin proof generation immediately after transaction acceptance      
2. **Batch Collection**: Obtain AcceptedIDMerkleRoot values in batches      
3. **Chain Verification**: After each batch, verify chain continuity by:      
   - Taking the last collected AcceptedIDMerkleRoot      
   - Hashing it with the next block's parent SequencingCommitment      
   - Verifying the result matches the next block's header SequencingCommitment field      
   - This confirms the previous block remains in the selected chain      
4. **Continue Progression**: If verification succeeds, obtain the next batch of accepted transaction IDs      
5. **Complete to Pruning Point**: Continue until reaching the next pruning point for verifiability
6. **Verify Finality Depth**: Confirm the pruning point has achieved sufficient finality depth from the current virtual
state, ensuring permanent verifiability before considering the proof complete 
      
The verification step uses the same calculation as consensus:
`hash(parent.SequencingCommitment, current.AcceptedIDMerkleRoot) == current.SequencingCommitment`.

# Cryptographic Commitments in Block Headers    
  
KIP-19 leverages Kaspa's block header commitments for secure inclusion proofs. While headers contain 13 fields, only the  
`accepted_id_merkle_root` (SequencingCommitment) is used as verification endpoints in KIP-19 proofs.  
  
## Security Model    
  
Any header field can contain arbitrary data with valid PoW. Without preserving the complete header chain to a permanent  
pruning point, such data cannot be verified and could be forged. KIP-19 achieves security by preserving the  
AcceptedIDMerkleRoot (transaction ID merkle roots) for every block from the transaction block to a permanent pruning  
point, creating a verifiable cryptographic commitment that proves transaction data authenticity.  
  
## Key Fields    
  
- **Accepting block's selected parent `accepted_id_merkle_root`**: Starting point for chain verification  
- **Pruning point's `accepted_id_merkle_root`**: Final verification anchor  
- **Preserved AcceptedIDMerkleRoot values**: Intermediate transaction ID merkle roots for each block in the chain

### Verification Process  

The verification process confirms:

1. Transaction authenticity through Merkle proof inclusion  
2. Chain connectivity through commitment verification to a permanent pruning point  
3. Final validation against the pruning point's known commitment  
  
Implementers should follow the established cryptographic commitment chain pattern where each block's
SequencingCommitment incorporates its parent's commitment with its own AcceptedIDMerkleRoot.

# Multi-Transaction Support  
  
## Batch Proof Concept  
  
KIP-19 supports batch proofs that can verify multiple transactions efficiently. Batch proofs share a single chain proof
while including individual transaction proofs for each transaction, providing significant efficiency gains for
applications needing to verify multiple transactions.
  
## Benefits  
  
- Reduced proof size through shared chain verification  
- Faster verification for multiple transactions  
- Efficient storage and transmission

# Security Considerations  
 
## Proof Forgery Resistance  

Merkle proofs provide logarithmic security per tree level - forging requires finding hash collisions in the Blake2b hash
function.

## Domain Separation Security  

Blake2b domain separators (`TransactionID`, `MerkleBranchHash`) prevent cross-protocol attacks between signing and proof
systems.

## Chain Verification Attacks  

The chain proof verifies both the AcceptedIDMerkleRoot calculation (derived from transaction IDs) and the
SequencingCommitment chain through merkle hashing. Since each block's SequencingCommitment is cryptographically
committed by combining the selected parent's SequencingCommitment with the current block's AcceptedIDMerkleRoot, the
entire chain cannot be forged without breaking the underlying Blake2b hash function.

## Privacy Implications  

Inclusion proofs reveal transaction output scripts and amounts since these are included in the transaction ID
calculation, but input signature scripts remain private as they are excluded from the txid. While full transaction bytes
are required for verification, the merkle proof only exposes the spending conditions and values, not the actual
authorization data.
  
## Resource Analysis    
    
### Proof Size Estimates    
  
Chain proof dominates total proof size, with merkle proof adding minimal overhead. Exact sizes vary based on network  
conditions and implementation choices.  
  
### Proof Size Considerations    
  
Chain proofs have a minimum size bound equal to the distance from the accepting block to the next pruning point, which  
cannot be reduced through technical optimizations. The only strategy to create smaller proofs is timing transaction  
inclusion to occur closer to the next pruning point by calculating when the next finality epoch will rollover. Since  
each proof requires obtaining all transaction IDs from every block in this range through sequential data acquisition  
processes, both intentional bandwidth consumption and unintentional resource exhaustion remain concerns when  
multiple applications simultaneously request proofs. Implementations should consider request management and  
validation costs to prevent resource exhaustion.

# Backwards Compatibility

This KIP introduces a new optional proof system without modifying existing consensus rules, block validation logic, or
network protocols. All existing node software and clients will continue to operate without any changes.

```
@dataclass  
class TransactionProofNode:  
   """Merkle proof node with direction tracking (for tx inclusion up to accepting_block.accepted_id_merkle_root)"""  
   hash: bytes  # 32 bytes
    
   is_right: bool  # Whether this hash is on the right side  
  
@dataclass  
class ChainProofNode:  
   """Merkle proof node without direction (for chain proof - space optimized - every chain proof calculates the left
   node from accepting_block.sequencing_commitment to future_pruning_point)"""  
    
   hash: bytes  # 32 bytes
  
@dataclass  
class ProofOfInclusion:  
   """Optimized proof structure for transaction inclusion in Kaspa"""  

   # Core proof data  
   transaction_bytes: bytes  # Full transaction to prove, hashing this to tx_inclusion_proof[0].hash ensures tx data matches (checksum when not proving, proof when proving)  
   tx_inclusion_proof: List[TransactionProofNode]  # [tx_to_prove_tx_id, sibling_node, sibling_node,...,sibling_node], hashing this to chain_proof_to_pruning_point[0].hash ensures data matches (checksum)
   accepting_block_sp_sequencing_commitment: bytes  # 32 bytes, this is the ONLY left node in the chain merkle proof
   chain_proof_to_pruning_point: List[ChainProofNode]  # [accepting_block_accepted_id_merkle_root, accepting_block_selected_child_accepted_id_merkle_root,...,pruning_point_accepted_id_merkle_root]  
     
   # Checksum/validation fields  
   future_pruning_point_sequencing_commitment: bytes  # 32 bytes  (checksum only, this is NOT a required component of proving since future_pruning_point_sequencing_commitment is preserved forever)  
     
   # Metadata  
   future_pruning_point_index: int  # Index of the next pruning point moving forward from tx_to_prove, for lookup in PastPruningPointsStore

   # Workflow = transaction_bytes -> tx_to_prove_tx_id -> accepting_block_accepted_id_merkle_root -> future_pruning_point_sequencing_commitment

```

### Verification Algorithm  

1. **Initialize**:   
   - Let TX_BLOCK be the block accepting the transaction we are proving
   - Hash TX_BLOCK.TX to get TX_BLOCK.TX.TXID  
  
2. **Verify TXID in AcceptedIDMerkleRoot**:   
   - Verify Merkle Proof from TX_BLOCK.TX.TXID to TX_BLOCK.AcceptedIDMerkleRoot  
  
3. **For each block from TX_BLOCK to pruning point P**:  
   a. Get AcceptedIDMerkleRoot:  
      - If current block is TX_BLOCK: use TX_BLOCK.AcceptedIDMerkleRoot  
      - Otherwise: retrieve preserved AcceptedIDMerkleRoot  
   b. Get parent's SequencingCommitment: retrieve preserved current_block.SelectedParent.SequencingCommitment  
   c. Verify commitment:  
      ```  
      hash(current_block.SelectedParent.SequencingCommitment, current_block.AcceptedIDMerkleRoot) == current_block.SequencingCommitment  
      ```  
   d. Move to next block in chain: current_block = current_block.SelectedChild  
  
4. **Final verification**: Ensure preserved P.AcceptedIDMerkleRoot hashes to recognized pruning point P.SequencingCommitment
  
### Hash Function Specifications  

#### Algorithm  

Blake2b with 32-byte digests

#### Domain Separation  

Uses `TransactionID` and `MerkleBranchHash` keys for inclusion proofs

#### Encoding  

Little-endian for numeric fields, natural byte order for hashes
  
## B. Implementation Notes  
  
### Potential Optimizations for Nodes  

The current chain proof generation is fundamentally inefficient because it requires retrieving all accepted transaction
IDs for every block along the selected parent chain path from the accepting block to the pruning point, then locally
calculating each AcceptedIDMerkleRoot. Since nodes only return transaction ID lists via the current API and don't cache
the pre-calculated AcceptedIDMerkleRoot values (even though they're computed once when creating the sequencing
commitment), each proof must reconstruct these roots by fetching the complete mergeset transaction IDs in order of
inclusion for every chain block. This creates unnecessary data transmission and computational overhead, as the same
calculations are repeated locally for what could be directly available as cached values, however evaluating the
cost/benefit is out of scope for kip19

```python
@dataclass  
class TransactionProofNode:  
    """  
    Merkle proof node for transaction inclusion proof.  
      
    Serialization format:  
    - hash: 32 bytes (Blake2b hash, natural byte order)  
    - is_right: 1 byte (boolean, 0x00 for false, 0x01 for true)  
    """  
    hash: bytes  # 32 bytes - Blake2b hash  
    is_right: bool  # Whether this hash is on the right side in the Merkle tree  
      
    def serialize(self) -> bytes:  
        """Serialize the proof node to bytes."""  
        return self.hash + (b'\x01' if self.is_right else b'\x00')  
      
    @classmethod  
    def deserialize(cls, data: bytes) -> 'TransactionProofNode':  
        """Deserialize from bytes."""  
        if len(data) != 33:  # 32 bytes hash + 1 byte boolean  
            raise ValueError("Invalid TransactionProofNode size")  
        return cls(  
            hash=data[:32],  
            is_right=data[32] == 0x01  
        )  
  
@dataclass  
class ChainProofNode:  
    """  
    Chain proof node for SequencingCommitment chain.  
      
    Serialization format:  
    - hash: 32 bytes (Blake2b hash, natural byte order)  
      
    Note: Direction is calculated sequentially, not stored.  
    """  
    hash: bytes  # 32 bytes - Blake2b hash  
      
    def serialize(self) -> bytes:  
        """Serialize the chain proof node to bytes."""  
        return self.hash  
      
    @classmethod  
    def deserialize(cls, data: bytes) -> 'ChainProofNode':  
        """Deserialize from bytes."""  
        if len(data) != 32:  
            raise ValueError("Invalid ChainProofNode size")  
        return cls(hash=data)

def calculate_merkle_root_from_proof(proof_nodes: List[TransactionProofNode], tx_id: bytes) -> bytes:  
    """Calculate Merkle root from tx_inclusion_proof."""  
    current_hash = tx_id  
    # Hash through all nodes except the first (which is the tx_id itself)  
    for node in proof_nodes[1:]:  
        if node.is_right:  
            current_hash = hashlib.blake2b(current_hash + node.hash, digest_size=32).digest()  
        else:  
            current_hash = hashlib.blake2b(node.hash + current_hash, digest_size=32).digest()  
    return current_hash

    """

    - version: 2 bytes (u16)  
    - inputs_count: 8 bytes (u64)

    tx.extend(struct.pack('<B', 1))

    # value

def verify_merkle_proof_for_creation(proof_nodes: List[TransactionProofNode], tx_id: bytes) -> bytes:  
    """Helper function to calculate Merkle root for proof creation."""  
    current_hash = tx_id  
    # Hash through nodes [1] to [-2] (exclude first and last nodes)  
    for node in proof_nodes[1:-1]:  
        if node.is_right:  
            current_hash = hashlib.blake2b(current_hash + node.hash, digest_size=32).digest()  
        else:  
            current_hash = hashlib.blake2b(node.hash + current_hash, digest_size=32).digest()  
    return current_hash

    print(f"    Step 1: Verify transaction ID matches proof[0]")  
    if proof_nodes[0].hash != tx_id:  
        print(f"    ✗ Transaction ID mismatch")  
        print(f"      Calculated: {tx_id.hex()}")  
        print(f"      Expected:   {proof_nodes[0].hash.hex()}")  
        return False  
    print(f"    ✓ Transaction ID matches")  
      
    # Step 2: Start with transaction ID and hash through sibling nodes  
    current_hash = tx_id  
    print(f"    Step 2: Building Merkle root from transaction ID")  
      
    # Hash through nodes [1] to [-2] (exclude first and last nodes)  
    for i, node in enumerate(proof_nodes[1:-1], 1):  
        if node.is_right:  
            print(f"      Hash {i}: hash(current + sibling)")  
            print(f"        current: {current_hash.hex()[:16]}...")  
            print(f"        sibling: {node.hash.hex()[:16]}... (right)")  
            current_hash = hashlib.blake2b(current_hash + node.hash, digest_size=32).digest()  
        else:  
            print(f"      Hash {i}: hash(sibling + current)")  
            print(f"        sibling: {node.hash.hex()[:16]}... (left)")  
            print(f"        current: {current_hash.hex()[:16]}...")  
            current_hash = hashlib.blake2b(node.hash + current_hash, digest_size=32).digest()  
        print(f"        result: {current_hash.hex()[:16]}...")  
      
    # Step 3: Verify calculated root matches expected root  
    print(f"    Step 3: Verify calculated root matches expected root")  
    expected_root = proof_nodes[-1].hash  
    print(f"      Calculated: {current_hash.hex()}")  
    print(f"      Expected:   {expected_root.hex()}")  
      
    if current_hash != expected_root:  
        print(f"    ✗ Merkle root mismatch")  
        return False  
      
    print(f"    ✓ Merkle proof verified successfully")  
    return True

def verify_proof_of_inclusion_complete(  
    proof: ProofOfInclusion,  
    pruning_point_header: 'Header'  # Retrieved from Kaspa node  
) -> bool:  
    """  
    Complete verification of proof of inclusion from transaction to pruning point.  
    """  
    try:  
        print("=== KIP-19 Proof of Inclusion Verification ===\n")  
          
        # Step 1: Verify transaction ID from serialized transaction  
        print("Step 1: Verify transaction from serialized bytes")  
        tx_id = calculate_transaction_id(proof.transaction_bytes)  
        print(f"  Transaction ID: {tx_id.hex()}")  
          
        # Step 2: Verify Merkle proof to accepting block's accepted_id_merkle_root  
        print("\nStep 2: Verify Merkle proof to accepting block")  
        if not verify_merkle_proof(proof.tx_inclusion_proof, tx_id):  
            return False  
          
        # Verify the calculated root matches the checksum field  
        calculated_root = verify_merkle_proof_for_creation(proof.tx_inclusion_proof, tx_id)  
        if calculated_root != proof.chain_proof_to_pruning_point[0].hash:            
            print("  ✗ Merkle root checksum mismatch")  
            return False  
        print("  ✓ Merkle root checksum matches")  
          
        # Step 3: Recreate the commitment chain from accepting block to pruning point  
        print("\nStep 3: Verify commitment chain to pruning point")  
        current_sequencing_commitment = proof.accepting_block_sp_sequencing_commitment  
        print(f"  Starting with accepting block SP sequencing commitment: {current_sequencing_commitment.hex()[:16]}...")  
          
        for i, chain_node in enumerate(proof.chain_proof_to_pruning_point):  
            print(f"  Block {i}:")  
            print(f"    Parent commitment: {current_sequencing_commitment.hex()[:16]}...")  
            print(f"    Current accepted_id_merkle_root: {chain_node.hash.hex()[:16]}...")  
              
            # Calculate next sequencing commitment  
            next_sequencing_commitment = hashlib.blake2b(  
                current_sequencing_commitment + chain_node.hash,  
                digest_size=32  
            ).digest()  
            print(f"    Next commitment: {next_sequencing_commitment.hex()[:16]}...")  
            current_sequencing_commitment = next_sequencing_commitment  
          
        # Step 4: Verify final commitment matches pruning point's accepted_id_merkle_root  
        print(f"\nStep 4: Verify final commitment matches pruning point")  
        print(f"  Calculated final commitment: {current_sequencing_commitment.hex()}")  
        print(f"  Pruning point accepted_id_merkle_root: {pruning_point_header.accepted_id_merkle_root.hex()}")  
          
        if current_sequencing_commitment != pruning_point_header.accepted_id_merkle_root:  
            print("  ✗ Chain verification failed")  
            return False  
          
        # Step 5: Verify the pruning point sequencing commitment checksum  
        print(f"\nStep 5: Verify pruning point checksum")  
        if proof.future_pruning_point_sequencing_commitment != pruning_point_header.accepted_id_merkle_root:  
            print("  ✗ Pruning point sequencing commitment checksum mismatch")  
            return False  
        print("  ✓ Pruning point checksum matches")  
          
        print("\n✓ Full cryptographic verification successful")  
        print(f"  Transaction ID: {tx_id.hex()}")  
        print(f"  Merkle proof length: {len(proof.tx_inclusion_proof)} nodes")  
        print(f"  Chain length: {len(proof.chain_proof_to_pruning_point)} blocks")  
        print(f"  Final commitment matches pruning point")  
          
        return True  
          
    except Exception as e:  
        print(f"Verification error: {e}")  
        return False
```
